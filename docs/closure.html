C6 - Test one assumption: "one long session is cheaper than splitting"

The owner asked for one session; the engine's budget says 5 to 6. The assumption behind running long is that one session avoids the re-reading cost of each new start (preflight, SETTLED, brief, handover). Tested on cache read, the metered quantity that dominates usage (standing instructions were 60 to 68% of effective usage in every read).

What was measured (_sessions/_cost/)

The conversation was summarised twice: once during Build (marker S1_G3_segment1_marker.json) and once during Publish. The usage skill counts only the part since the last summary, so the session has three segments.

Segment Read Requests Cache read Per request
A: start to the first summary G0 21 4,641,715 221,034
A G1, Discover 114 40,917,329 358,924
A G2, Design 155 63,227,855 407,922
A Build before the first summary not on record
B: first to second summary G3, Build exit 228 107,463,234 471,330
B Publish before the second summary not on record
C: after the second summary Close read 79 22,353,048 282,950

Within segment A, the marginal cost per request rose from 221k (start) to 390k (Discover, G0 to G1) and 544k (Design, G1 to G2): about 2.5 times, with the work getting no heavier per request. Segment C, starting from a summary, ran at 283k. Segment B also started from a summary but ran 228 requests, and averaged 471k.

What this shows

Cost per request is driven by how long the conversation has run since its last reset, a summary or a new session. The two automatic summaries did most of what a planned split would have done to the token bill, so the token saving of a planned split over this session cannot be measured from these reads. An upper bound only: had segment B run at segment C's 283k, it would have read about 64.5M instead of 107.5M, about 22% of the recorded total. That is not an estimate, because Build's requests carried heavier tool output than Close's.

What the unplanned summaries did cost is measurable: two stretches of work have no usage record (Build before the first summary, Publish before the second), and the summaries dropped detail that the record then had to be rebuilt from files (C8, and this section's first draft, which read G3 as cumulative and had to be rewritten).

Confounds

  • Build and Publish carried heavier tool output (DAX results, logs, captures) than Discover or Close.
  • Summaries happen when the context fills, not at a gate, so segment lengths are not chosen.
  • Quality: no defect was traced to a summary or to the absence of a split.

Conclusion

The assumption is not supported: a long session does not save tokens, because the history it carries makes each later request dearer (2.5 times within one segment here). It is not refuted on totals either, because the automatic summaries reset the history twice. The case for splitting at a gate is that it puts the reset where the work allows one, with a usage read and a handover first, instead of mid-Build with neither. P24's finding (§114, splitting saved almost nothing) was measured on short sessions with no long build tail; the two do not conflict.
